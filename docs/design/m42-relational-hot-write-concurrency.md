# SonnetDB 关系热点写与并发控制方案

日期：2026-10-10（Asia/Shanghai）。状态：**规划，未实施、未压测、性能未验收**。

归属：[ROADMAP](../../ROADMAP.md) 的 V45-X09 / M42-H01~H07；关联 M39 事务/触发器合同、V45-X02 资源治理和 V45-X06 固定基线。全部 H 工作包为 4.5 必选范围，首批支持边界如下；不改变 Workbench Preview 1 当前执行顺序，不将本专项自动加入预览发布前置条件。规划 ID 不是已创建的 issue/PR。

## 1. 要解决的问题与现有基础

目标是减少关系写入中不必要的串行等待，在高竞争时控制排队和尾延迟，同时保持每个请求的结果、事务原子性与持久性。热点行指多个并发请求反复更新同一条记录；必须分别识别同键冲突、同表不同键互阻、同库不同表互阻和 WAL 刷盘成本，不能把它们统称为“一行一把锁”的问题。

2026-10-10 核查基于本地 `main` 源码，规划起点 HEAD 为 `60bd752f95c1ef2dcbab2566925cd599c43383f4`；相关产品源码当时无未提交修改。后续实现和基准须另行绑定实际候选，不把本文件起点当作性能证据。

| 当前代码证据 | 已有能力 / 限制 | 对方案的要求 |
|---|---|---|
| [TableStore](../../src/SonnetDB.Core/Tables/TableStore.cs)：`_sync`、`InsertMany`、`ApplyBatch` | 每表共享互斥锁；已有批量多行写入。 | 复用批量接口，区分减少获取次数与缩小竞争范围；批次过大可能拉长其他请求等待。 |
| [TableSqlExecutor](../../src/SonnetDB.Core/Sql/Execution/TableSqlExecutor.cs)：`ExecuteUpdate`、`ExecuteBoundUpdate`、`CommitTransaction` | 普通非 UDF UPDATE 在表管理锁内扫描、求值并提交；显式提交另处理延迟触发器。 | 锁外准备后必须重新验证，不能无条件使用过期读值；UDF/触发器不能随意重试。 |
| [TableManager](../../src/SonnetDB.Core/Tables/TableManager.cs)：`ApplyTransactionCore`、`AcquireReadSnapshots` | 同库管理锁内获取各表锁、检查约束并提交；关系读快照也使用该协调边界。 | 不能只改写入锁而破坏跨表可见性、外键、DDL 或读快照。 |
| [TableTransactionJournal](../../src/SonnetDB.Core/Tables/TableTransactionJournal.cs) 与 `ApplyTransactionCore` | 多表事务共享 `transaction.sdbtxn`，使用 before-images、各表 WAL 同步和提交标记。 | 在新的恢复协议通过前，共享日志仍必须受单写者协调；不得直接移除管理锁。 |
| [KvKeyspace](../../src/SonnetDB.Core/Kv/KvKeyspace.cs)：`ApplyBatch`、`CommitPlannedMutationBatchLocked` | 一批 mixed put/delete 可写成一个 WAL record；开启 `SyncWalOnEveryWrite` 时该批一次 fsync，keyspace 发布仍受锁保护。 | 批量记录不等于多个独立事务的组提交；上层细锁不自动消除底层串行点。 |
| [SqlTransactionContext](../../src/SonnetDB.Core/Sql/Execution/SqlTransactionContext.cs)：`AddOrMergeTableMutation` | 已归并同一事务内同键变更；`TableStore.PrepareBatchLocked` 会拒绝批内重复目标行，并校验原行状态/版本。 | 不把事务内归并称为跨请求分组；不能将多个独立同键 mutation 直接塞进现有批接口。 |
| [SonnetDbMeter](../../src/SonnetDB.Core/Diagnostics/SonnetDbMeter.cs) | 已有 `sonnetdb.lock.wait.duration`、固定 `lock.name` 分类及 WAL 同步计时。 | 复用指标并核实各入口覆盖；只补缺失的持锁、队列及批次观测，不重复造一套监控。 |

以上证明存在串行点，不证明生产已发生积压，也不提供最大 QPS 或优化倍数。现有隔离合同保持原样，本专项不升级为 Serializable 或完整 MVCC 承诺。

## 3. 锁与提交路径的改造方法

### 3.1 先有基线和准入，再缩短临界区

H01 对锁等待、持锁、候选扫描、约束/索引检查、WAL 追加、fsync、发布和响应分别计时。明确排队发生在 Server worker、管理器、表、keyspace 还是磁盘；把锁等待与 I/O 等待、乐观冲突和重试分开，观察各阶段覆盖率和监控本身的开销。

H02 复用现有执行预算，新增队列只在进入昂贵准备/锁等待前预留请求数与字节，按数据库总量、表/热点键份额及单批限制共同约束。等待时间计入端到端期限，队列项持有的 SQL/参数/行值也计内存；热键跟踪表、锁条带、缓存和完成结果保留均有容量/生命周期，不按无限主键创建永久对象。

必须配置并冻结：最大排队请求数、排队字节数、单批请求数/字节数、分组窗口、最老请求期限、最大在途批数、重试次数/总期限、关闭排空期限和公平份额。H01 未写出具体值和校准依据前，H02 不进入实现验收；这些是拟议配置合同，不是已有 public API。低负载允许立即提交，禁止为凑满批次无限等待或用忙等追求微秒定时精度。

H03 将可安全重做的解析后准备、编码和候选计算移到大锁外；持锁后核验 schema 版本、table/keyspace generation、原行状态/版本、约束依赖，再应用已准备的变更。冲突只在明确无副作用、尚未持久化的边界内做有次数及总时限的重算，不能静默覆盖其他更新。

### 3.2 先隔离独立表，再处理同表异键

必须先定义并覆盖 SQL、直接 TableStore API、批量接口、触发器/级联、维护任务、DDL/TRUNCATE 和读取快照的共同协调协议；不能只优化 Server 的一个 UPDATE 入口。固定锁顺序按稳定对象身份及主键/索引键编码制定，catalog/schema 代际防止 DROP/recreate 后误用旧对象，名称绑定继续遵守 GH-Issue #211。

第一阶段优先使无跨表约束依赖的不同表写入独立准备和提交。仍涉及共享 `transaction.sdbtxn` 的多表事务由专门提交协调边界串行保护；它与普通单表写入必须获取兼容的表/依赖锁，使外键、级联和跨表快照看不到半提交。若解除管理锁必须更换恢复格式，则先单独完成日志版本、迁移/拒绝和故障验收，不以性能 PR 顺带更改格式。

第二阶段由 H01 证据在有限条带锁与乐观准备之间选型。条带哈希冲突只影响并发度，不得影响正确性；锁表大小固定或有明确上限。乐观方案复用原行状态/版本，并处理删除重插、主键变更、同唯一值的不同主键和读取集合变化。多行条件更新不能仅验证命中行就声称避免幻读/write skew；需要范围/依赖保护的路径保留原协调，完整 MVCC 不列为本专项前置重写。

准备可以并发，KV/WAL 发布仍须有确定顺序。H04 必须同时测 keyspace 锁，不能把管理锁等待转移到 WAL 锁后宣布解决；底层发布和刷盘成本由 H05 接续。

### 3.3 组提交保留独立事务语义

H05 在一个有界窗口内收集已经可提交的独立事务，按顺序追加可独立恢复/判断的记录，共用所需同步操作，按每个事务的 durable sequence/提交决定完成响应。不是把 N 个业务事务包装成一个大业务事务，也不是关闭 `SyncWalOnEveryWrite` 来取得漂亮数字。

设计评审必须明确：每事务记录边界和提交标记、组内失败隔离、原子内存发布点、读快照可见性、截断尾记录恢复、WAL/提交标记同步顺序，以及多表 journal 的独立约束。首批组提交可限定单表事务；多表仍走已验证路径并参与共同协调，不能从单表一次 fsync 推导多表已持久。

在 required durability 尚未满足时不得成功响应。追加或 fsync 失败后，能够证明未提交的请求返回明确失败；可能已持久化而未确认的请求保持 unknown，按既有恢复合同处理。禁止自动回滚可能已提交的事务，禁止透明重试未知结果。取消在 WAL 前可以撤出；进入不可撤回阶段后，取消/网络断连不是回滚证明。内存发布、最终响应和恢复判定须有逐点故障测试。

### 3.4 热点行分组只优化可证明等价的子集

H06 初始允许单表、完整主键等值定位、自动提交、确定性整数计数/库存更新，列类型和溢出规则沿用原引擎。例如 `UPDATE inventory SET stock = stock - 1 WHERE id = @id AND stock > 0`：组内请求按确定顺序在私有行状态上逐次重判 `WHERE`、求值和检查，各自保留影响行数与错误；库存不足的请求不能扣减，也不能因为同组另一个失败而丢失已接受请求的结果。

首批排除显式多语句事务、多行/范围/子查询 UPDATE、修改主键或索引键、跨表外键/级联依赖、触发器/deferred/outbox、UDF/非确定函数、`RETURNING` 及未证明等价的版本列行为。排除表示沿用现有语义路径，不拒绝原先受支持的 SQL；原路径与快路径必须共享冲突/发布协议，切换或冷却热键前先排空或建立顺序屏障。

Leader 定位行并建立私有执行状态，Follower 复用定位和协调成本；组内仍逐请求执行，不把多次加减简单求和，不对独立请求做 last-write-wins。当前 `PrepareBatchLocked` 不接受同批重复行，`AddOrMergeTableMutation` 只适用于同一事务；新执行器必须保留独立操作及提交决定，不能直接复用该归并来吞掉中间结果。校验失败的请求不污染后续私有状态，持久化失败时依 H05 判定，不能补造成功。

分组缓存绑定数据库、表对象/generation、schema 与主键，容量和生命周期受 H02 约束。持久化中间状态对其他读者不可见；组内已序列化的请求和外部读写必须能构造符合现有隔离合同的历史。默认启用前记录命中、拒绝/回退原因、批大小、窗口实际等待与调度抖动。

## 4. 基准方法与执行边界

| 场景 | 固定工作负载 | 要区分的问题 |
|---|---|---|
| A 同一行 | 一个主键的计数加一、有限库存扣减及失败请求混合 | 真正同键争用、每请求条件/结果与分组收益。 |
| B 同表不同行 | 均匀且不相交主键，另设唯一索引竞争子例 | 表锁/索引锁/底层 WAL 竞争，不能把异键假定为无约束冲突。 |
| C 同库不同表 | 无依赖表并行；外键/跨表事务另组 | 管理器粗锁和恢复协调成本。 |
| D 控制与混合 | 不同数据库；热点/冷键混合、读写混合、大批和小写竞争 | 进程总预算、跨库公平性、普通流量 P99、饥饿。 |

先固定主键数量、表/索引/schema、行宽、查询计划、数据种子、客户端与持久性，不将完整笛卡尔积一次跑满。分别比较单条自动提交、既有单事务多行批量、H05 组提交、H06 热点分组，清楚标记事务边界差异。均匀/倾斜分布、热/冷缓存、checkpoint/维护压力分组报告。

开发基准先 1 次、1 客户端、最多 100 操作且 10 秒的微试；随后每个预约批次最多 24 个 case，每 case 预热最多 10 秒、测量最多 30 秒且最多 100,000 请求，二者任一达到即停止；统一外层 20 分钟截止，超预算不自动加跑。并发候选为 1/4/16/64，最终上限取机器预算与已冻结准入较小值；所有 case 串行运行，提供取消标志、每 30 秒进度及超时收口。失败复现最多两次且共用原批次截止，原失败保留。

吞吐测试记录成功、冲突、明确失败、取消、拒绝和 unknown 的各自数量与分母。固定并发测试之外，另做有上限的到达率/过载测试，端到端延迟包含准入和分组等待，避免只统计进入执行器后的时间或由闭环客户端掩盖排队。不能在响应后才记耗时，不能只报平均值或成功请求 QPS。

开发数据只用于机制和回归。H07 冻结真实 embedded 与 Server/ADO 或 Frame 客户端路径、x64/ARM64 机器/盘/文件系统/运行时/commit 和相同持久性配置；保留原始请求账本与直方图。外部对照只比较语义、事务边界、持久性和资源一致的子集；不得拿厂商公开峰值代替同条件结果。

168 小时属于独立运行合同：最多 168 小时，检查点至多 1,008 次（每 10 分钟一次），外层另设一次最多 10 分钟收口期限；明确取消、资源阈值、失败后停止/保留证据和执行主机所有权。不得通过工具长时间阻塞等待或无限自动续跑；缺少目标机或运行预算记 NOT_RUN。

长命令均记录 PID、创建时间、完整命令行、父链和输出；检查并只回收本任务确认归属的子进程/临时数据库。固定测试目录与取消文件，删除前核对绝对路径；不操作用户数据库、共享缓存和未知进程。无需广域发现编译器或安装依赖。

## 5. 正确性、恢复与放行条件

| 门禁 | 必须取得的证据 |
|---|---|
| 逐请求语义 | 计数最终值与实际提交集合一致；库存不超卖；WHERE 不满足、溢出、唯一/外键/CHECK、失败请求不污染后续请求；保存每请求影响行数/错误并与原路径和可接受串行历史对照。 |
| 并发与可见性 | 丢失更新、删除重插/ABA、更新主键、唯一键竞争、事务回滚、read-your-writes、既有跨表读快照、DDL/TRUNCATE、维护任务；无新增死锁/饥饿或隔离承诺。 |
| 故障恢复 | WAL 追加前/中/后、同步前/失败/后、提交决定前/后、内存发布前/后、响应前断连及 hard-kill/reopen；所有已确认成功满足对应持久性配置，unknown 逐项恢复对账而不盲重放。正常关库重开不替代崩溃测试。 |
| 组内与批次隔离 | 首/中/末请求校验失败、超时、取消、部分写入、坏尾记录、不同批同时在途；一请求失败不能被改成整组成功，独立事务不能意外变成同生共死。 |
| 资源与公平性 | 数量/字节/最老等待/在途批/线程/CPU/heap/GC 全部受限；过载有明确拒绝，热点不能饿死普通键、其他表/库或读取，关闭后队列/缓存/锁状态被回收。 |
| 性能与成本 | A/B/C 与控制组各自的吞吐、P50/P95/P99、锁等待/持锁、WAL 字节、fsync 次数/耗时、分配/工作集/CPU；同时报告失败率与观察开销，不只选获益 case。 |

H01 在实现前形成机器可读门槛清单：每场景的最小吞吐收益或最大回退、端到端 P95/P99 上限、普通流量回退、排队与内存/CPU 上限、最大拒绝率及正确性/恢复零容忍项。数值须由至少三次有界基线、噪声区间和目标负载确定并冻结；本规划不虚构已校准倍数。H07 同配置比较至少三次，候选若改动则重跑受影响范围；不得看完结果后降门槛或通过关闭持久性取胜。

不同表并行、同表异键优化、组提交和热点分组分别验收，不互相替代。若某机制不达标，回退设计或经明确范围评审登记 DEFERRED，不能把必选范围静默删除后宣布完成。功能合同、本地测试、真实服务、硬件性能、崩溃与长稳六类状态分列。

所有新策略默认关闭或仅由内部实验配置启用，H07 通过后再评审默认值和分阶段放量。关闭策略须停止接收新快路径请求、在期限内处理在途批并保持逐请求终态；不可恢复的在途状态保持 unknown。运行时回退使用同一持久格式的兼容旧路径；二进制降级只有在旧 writer 被证明兼容时允许，否则拒绝旧 writer 并提供迁移/恢复说明。

Core 保持 Safe-only、零第三方运行时依赖，新增配置/诊断 DTO 使用 source-generated JSON，相关 AOT/trim 警告为零。公开 API、SQL 名称、错误/影响行数和默认持久性保持兼容；确需落盘格式变化须独立版本化并同步 CHANGELOG/迁移或拒绝策略。每次实际代码提交前仍执行仓库要求的完整 restore 和原 Format Check。

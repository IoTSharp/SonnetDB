# 关系表主键 schema 迁移

GH-Issue #226 在已有主键重命名的基础上，支持有存量数据的主键类型和定义迁移。迁移预先验证全部目标行、索引与约束，在一份恢复日志保护下更新相关表，最后发布新的目录和内存 schema。

## SQL 入口

```sql
-- 已有 STRING 主键中的每个值必须能够无损转换。
ALTER TABLE parents ALTER COLUMN id TYPE INT;

-- 用已有列替换主键；目标列必须非 NULL 且整表唯一。
ALTER TABLE parents ALTER PRIMARY KEY (code);

-- 无主键表可以为已有数据增加单列或复合主键。
ALTER TABLE items ADD PRIMARY KEY (tenant, code);
```

已有列名保留原始拼写，名称绑定沿用未引用名称忽略大小写、双引号名称精确匹配的合同。目录、`GetSchema` 与新 reader 返回迁移后的列类型和主键定义。

`ALTER COLUMN ... TYPE` 使用严格 schema 转换：不可转换、溢出、需要舍入、整数精度丢失和非有限 FLOAT 均拒绝。超出 Decimal 值域的整数字符串用精确整数比较验证 FLOAT 转换；无法证明无损的非整数文本保守拒绝。目标 DECIMAL 声明同时验证 precision/scale。目标默认值也须满足新类型、长度和非空要求。

本变更没有新增 SQL `DROP PRIMARY KEY` 或空 `PRIMARY KEY()` 语法。管理器已有的空主键定义入口可完成无入站外键表的内部迁移；该测试路径不表示 SQL 已支持移除主键。

## 行、索引和外键

迁移保留行的业务内容，并重新编码主键及普通/唯一索引。对已有父表主键的普通入站外键，以旧父行身份定位新父行，按新主键顺序更新子表外键值、类型和引用声明；即使新旧键值交换，子行仍指向同一个父行。复合主键按全部分量定位。含 NULL 的子外键沿用 MATCH SIMPLE，非 NULL 分量仍须满足目标类型。

预检检查主键重复、NULL、唯一索引、CHECK、DECIMAL、长度、外键和 KV 单键/值限制。任一检查失败时，不发布目录屏障或写入源行。父子表已有约束、默认值、注释及未改变的列属性随 schema 克隆保留；AUTO_INCREMENT 高水位不重置，现有 ROWVERSION 不因 DDL 递增。后续 INSERT 继续使用既有默认值、自增和 ROWVERSION 规则；失败 INSERT 是否耗号仍遵循原有合同。

以下拓扑在预检阶段明确拒绝：

- 自引用外键，或多个外键共享需要改写的子表列。
- 存在入站外键时改变主键列数或移除主键。
- 需要改型的父主键列同时承担出站外键。
- 需要改写的子外键列是 AUTO_INCREMENT 或 ROWVERSION。
- 需要改写的子外键列也是主键，且该子表还被其他表引用。

生成主键列的类型变更、直接修改普通子外键列类型仍保留既有拒绝规则。DDL 不加入活动轻事务，跨语句 DDL 事务属于 #227。本合同不扩展普通主键 DML UPDATE 的支持范围。

## 与已有事务交错

ReadCommitted 和 Serializable 的每张缓冲写入表都绑定首次写入时的不可变 schema。其他连接迁移了该表或其父主键并更新其外键 schema 后，旧事务不能再把缓冲行按新定义读取、归并、展开级联或提交；返回 `table_serialization_conflict`。COMMIT 冲突会结束整个事务，调用方应从 BEGIN 重新读取并重试，不能只重发旧写集。

这一检查包含没有读取令牌的普通 INSERT、UPDATE、DELETE、INSERT 后 UPDATE 和级联操作；保存点撤销新增写集时同步移除新增 schema 绑定，保存点前的绑定保留。不相关表的迁移不使既有写集失效。最终验证位于 TableManager 提交锁内、级联/延迟触发器之前和持久提交之前，避免校验后发生另一轮迁移。

## 有界执行

单次迁移最多涉及 32 张参与或外键校验表，父子表合计最多 100,000 行。预检累计工作集预算为 256 MiB，恢复日志最多 1,000,000 条 before-image、16 MiB 原目录和 128 MiB payload；这些是逻辑预算，不能当作进程实际内存峰值保证。

预检先读取键和元数据，在复制值或读取磁盘值前检查预算；转换和约束校验逐行响应取消。raw 行/索引变更按已有 KV 维护批次上限分批，复用读预算和写 deadline，并同步 WAL。迁移持有相关表锁，不是后台在线迁移。超过限制时需先缩小数据范围；本功能没有自动拆分成多个可见迁移的行为。

## 持久化与回退

持久阶段顺序如下：

1. 以旧 schema 语义保存 `tables.tblschema` v13 屏障，并同步文件及目录。
2. 原目录、表 generation、schema 指纹和 raw before-images 写入 `tables/schema-migration.sdbddl`，同步文件及目录。
3. 分批写入全部参与表的行/索引，并同步各表 WAL。
4. 保存并同步新 schema 目录，目录版本保持 v13。
5. 写入并同步完成标记，随后发布内存 schema 和目录快照。

恢复日志使用 `SDBDDL01`、版本 1、24 字节头、payload/header CRC32 及 `SDBDLC01` 完成标记。截断的合法完成标记前缀仍视作未完成；其他损坏、重复条目或未知版本拒绝打开。

数据库重开时先处理迁移日志，再构造普通 TableStore 或重建索引。未完成日志必须具备 v13 屏障；所有表的指纹、目录和 generation 校验通过后，才开始幂等恢复旧行和旧 schema 语义。恢复期间再次终止可继续重放。恢复后的目录永久保持 v13，防止旧引擎在未完成日志期间插入写入。已可见的完成标记也会再次同步，确认成功后才允许新写。

Prepare 发布或完成标记同步结果不确定、补偿失败时，当前管理器和已开表停止服务，调用方必须关闭并重开数据库。不能把此类异常解释为已确定回滚，也不能在原句柄上直接重试写入。

v13 目录 payload 沿用 v12，普通目录保存和恢复不降低版本；本变更不修改 `FileHeader`、既有显式主键编码或行值 payload。旧引擎明确拒绝 v13，回退必须使用迁移前的完整数据库副本，不能仅改版本头或删除恢复日志。目录同步沿用仓库 `DirectoryFsync` 的文件系统支持合同；真实进程强制终止测试不等同于断电或损坏设备测试。

# GH-Issue #394：OwnsMany JSON 跟踪更新切片

截至 2026-11-05（Asia/Shanghai），本源码切片将 EF 已有 OwnsMany 对象数组的单元素及子树更新接入 SonnetDB SQL，新增 22 项合同，完整 EF 套件 **340/340 通过，0 失败、0 跳过**。**公开新 Provider 消费者与实际应用验收尚未执行，EF 10 的嵌套集合 ordinal 跟踪限制仍保留，不能关闭整个 #394。** 本次不重做 EF 的集合生命周期、物化或 JSON writer，不新增反射型 JSON 序列化入口。

## 实际缺口与最小修复

修改前，真实 embedded、REST 和 HTTP/2 Frame 三种模式均能插入并完整物化包含 OwnsMany 的 JSON 对象数组。三种模式在修改一个元素属性时均实际失败，原因是 `SonnetDbUpdateSqlGenerator.TryGetJsonUpdatePath` 与 `TryGetOwnedPath` 只接受 `IsUnique` ownership；这把集合元素路径统一拒绝为不支持的 JSON 操作。

本次只修改该更新路径的校验和编码。每一级属性名从 EF ownership 元数据取得，按完整名称匹配 EF 的原始路径；模型名里的点、引号、方括号及 Unicode 均作为名称处理，只有元数据表明是集合的位置才能读取数组序号。序号最多十位、使用不带符号的规范十进制、限制在 Int32 范围；缺少序号的集合片段只允许作为整集合替换的末端，不能误用于后续元素属性。

最终 SQL 路径按 SonnetDB 的带引号属性片段与明确数组序号重新编码，继续使用既有 `json_set_value`、参数绑定、JSON 片段开关与 EF metadata writer。跟踪命令中存在多个不同模型解释时仍拒绝歧义；最多 1024 个 entry/type、64 个路径片段、1024 字符的既有边界继续生效。

## EF 10 的嵌套 ordinal 限制

真实测试中，含二层 OwnsMany 的父数组删除首元素并追加新元素后，当前保存确实成功，持久 JSON 的顺序和值正确。但同一个仍跟踪的上下文随后再次清空集合时，EF 10.0.14 的 `ChangeDetector` 会报告嵌套 identifying FK（`CollectionPart.CollectionItem__synthesizedOrdinal`）属于 key、不能修改；异常发生在下一条 SQL 发出之前。

本次保留该原始失败及专门负回归，确认拒绝后没有新增 UPDATE、持久数据不变。需要在这种父集合结构变化后继续操作嵌套集合时，由应用显式 `ChangeTracker.Clear()` 并重新查询持久对象，再继续修改。Provider 没有绕过主键校验、伪造 EF 内部快照、自动重试写入或静默读取并回写 JSON。任意重排、跨 owner 迁移及无需刷新即可连续修改整个嵌套集合生命周期仍未因此宣称支持。

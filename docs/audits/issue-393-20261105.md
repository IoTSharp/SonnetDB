# Issue #393：受限自引用主键迁移

本次在 `a7125ffb15c3d2182ff811036173316c75329ba9` 基线上扩展既有持久 schema 迁移。自引用外键和其它入站子表使用同一份旧主键到新父行映射，同一份 journal 决定及目录发布。不是临时删除约束后逐条改表。

## 支持合同

- 主键替换必须保持被引用主键的列数；现有引用必须是旧主键的完整有序引用。新键仍经过 NOT NULL、唯一索引、CHECK 和类型校验。
- 自引用的源列不能与旧主键或新主键重叠，不支持生成源列、多外键共享源列或需要继续级联修改被其它表引用的子表主键。此类拓扑在任何持久写入前拒绝。
- 相关父子表及出站引用限定 `main` schema，整个关系目录不得有跨 schema 的同短名表。既有 schema 迁移 journal 仍按短表名恢复；本次在持久屏障前明确拒绝该不安全目录，不把成对 schema/table 身份的后续恢复改造混入此片。
- 主键类型变更沿用现有无损转换规则；本次不扩大类型转换集合。实际验证了 `INT → DECIMAL(18,0)`、按既有行身份将 `INT` 主键替换为另一个 `STRING` 列，以及复合键迁移。`INT → STRING` 仍不在既有严格转换集合中。
- 完整引用按父行映射，支持自环及循环引用。部分 NULL 沿用 MATCH SIMPLE，非 NULL 分量仍须符合新列的严格转换规则，不得猜测不存在的父行。
- 准备先冻结所有父行的新键，再准备自引用值，不依赖扫描顺序。两次准备都计入既有 100,000 行操作和 256 MiB 工作集预算；自引用有效行数受两次准备的合计预算约束。仍采用数据库排他 DDL 锁、相关表锁及取消检查。
- 没有修改目录、行、键或 journal 的二进制格式。沿用既有版本屏障、原子提交、未知持久决定后的访问封锁及重开恢复。

## 验证

新增真实数据库回归覆盖空/有数据表、主键替换及类型变更、循环和自环、外部子表、复合/部分 NULL、唯一/覆盖索引、碰撞和溢出预检、四个持久阶段的注入失败、提交 flush 结果未知、取消、后续 DML 和两次重开。

Crash 子进程新增自引用场景，分别在 journal、父表 raw、catalog 和 complete 边界强制终止，逐次重开核对主键及自引用/外部引用共同处于旧状态或已提交状态。暂停等待有 30 秒上限，父测试只终止其拥有的子进程。

本机原始 TRX、失败日志及 Cordonix 执行/清理回执保存在 `artifacts/branch-cleanup-20261105/`。最终通过数以该目录的收据及根 HANDOFF 为准；最初不支持的 `INT → STRING` 和 Crash 场景未注册等失败日志保留。

这些证据属于本机 Windows/.NET 10 源码和真实进程恢复；公开旧 5.0.0 包不会因源码修改而改变。未由此宣称任意 FK 拓扑、任意类型转换、物理掉电、介质损坏或生产数据验收。

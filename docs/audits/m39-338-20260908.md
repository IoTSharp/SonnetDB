# M39 #338 高级事务语义准入与验收

日期：2026-09-08。状态：#338 已完成下述范围的实现与本地验收；12 项门禁均有本次实际运行证据。本文记录提交前工作树的实测结果，源码身份以验证清单中的哈希为准，不将本地验收等同于远程合入或发布。

本切片实现单库关系表 SQL 提交阶段的延迟约束触发器，并提供显式调用的 durable outbox worker。准入依据是多条 DML 完成后的业务不变量检查：逐语句执行的 AFTER 触发器会读取中间状态，无法用相同检查体表达事务最终状态。语法、恢复和容量门禁已分别完成研发范围内验证；真实项目服务器上的固定硬件、外部消息系统和长期 SLO 转入 ROADMAP 的真机验证待办。

## 准入场景与取舍

账户余额转移是 #333 状态保护 journey 的多语句扩展：初始两行余额为 40、60；同一事务先将第一行改为 30，再将第二行改为 70，总额必须保持 100。立即 AFTER ROW 的检查体在第一次 UPDATE 后保存 90，最终 CHECK 会拒绝整笔转移；延迟约束检查体在 COMMIT 中读取总额，两次事件都取得最终的 100。测试同时保留立即触发器对照，不能只证明新增语法能执行。

示例只执行这一次转移，`balance_checks.id` 使用各事件对应账户标识：

```sql
CREATE TABLE accounts (id INT, balance INT, PRIMARY KEY (id));
INSERT INTO accounts (id, balance) VALUES (1, 40), (2, 60);
CREATE TABLE balance_checks (
    id INT, total INT, PRIMARY KEY (id), CHECK (total = 100));
CREATE CONSTRAINT TRIGGER balanced AFTER UPDATE ON accounts
DEFERRABLE INITIALLY DEFERRED FOR EACH ROW
LANGUAGE SQL AS BEGIN
    INSERT INTO balance_checks (id, total)
    SELECT NEW.id, total FROM (SELECT SUM(balance) AS total FROM accounts) AS totals;
END;
BEGIN;
UPDATE accounts SET balance = 30 WHERE id = 1;
UPDATE accounts SET balance = 70 WHERE id = 2;
COMMIT;
```

此次准入的最小合同为 `CREATE CONSTRAINT TRIGGER ... AFTER INSERT/UPDATE/DELETE ON table DEFERRABLE INITIALLY DEFERRED FOR EACH ROW ...`。普通触发器不接受 DEFERRABLE，约束触发器必须同时声明两个阶段标志；拒绝 INITIALLY IMMEDIATE、SET CONSTRAINTS、BEFORE/STATEMENT 约束触发器、约束 transition tables 和 AFTER COMMIT 语法。它不是 PostgreSQL deferred constraint 语义全集。

显式 order group 已评估：本场景只需要区分立即与提交两个阶段，并在同表、事件、时机、粒度和阶段内固定顺序。已有 FOLLOWS/PRECEDES 可表达该需求，新增命名 order group 没有产生额外业务能力，因此本切片不增加其语法。跨阶段的 FOLLOWS/PRECEDES 在创建或修改时拒绝，落盘和已发布定义保持原状态。

## 事件、顺序与事务边界

- 每条 SQL DML 固定入口触发器快照。立即 BEFORE/AFTER ROW 和 AFTER STATEMENT 保持既有分发顺序；延迟 AFTER ROW 按 DML 顺序、源行顺序、该行触发器持久顺序入队。空影响集不产生延迟行事件。
- COMMIT 以 FIFO 遍历队列，每个事件执行一次。延迟 body 引起的 SQL DML 可以追加新事件，放在已有队列之后；队列增长受相同预算和提交期限约束。旧队列不会因为同一行后续 UPDATE/DELETE 或最终净 mutation 归并而合并。
- OLD/NEW 是源事件捕获的行图像，保留 BEFORE 改写及事件对应的 ROWVERSION。`WHEN` 在提交阶段求值，但读取这些原始事件图像；它不会自动替换成该行最终版本。body 中的关系表 SELECT、聚合和 DML 读取当时已提交基线加本事务最终缓冲，以及队列中先前动作生成的变更。
- 无显式事务的源 DML 自动创建轻事务，先缓冲源写入和队列，再执行提交阶段。显式事务可跨多条 SQL DML 累积事件；COMMIT 前不会执行其延迟 body。
- 源 DML 或过程调用在既有事务内失败时，内部保存点同时撤销该次调用新增的 mutation、事件和队列内存计费，保留之前成功语句。这里的保存点是现有引擎内部合同，未增加用户可执行的 SAVEPOINT/ROLLBACK TO 语法。
- COMMIT 中的 body、预算、取消、依赖或最终约束失败会结束并撤销整笔事务；不能只撤销最后一个事件后继续提交。显式 ROLLBACK 和被放弃的事务脚本丢弃全部未执行事件。完成后的事务不能再次 COMMIT。
- 事件保留创建时的不可变触发器定义、原调用方和过程/触发器祖先链。之后 ENABLE/DISABLE、RENAME、DROP 或顺序调整影响后续 DML，已入队事件仍使用捕获定义。每个事件还固定其依赖关系表的 schema；提交时发现 schema 替换、删除或重建则返回 `routine_dependency`。

## 提交锁、级联与执行预算

提交阶段通过 `TableManager` 的互斥锁把最终状态读取、延迟动作、约束检查和持久化写入串联。通过同一 SQL/TableManager 路径提交的并发事务不能在检查与写入之间插入另一笔提交；仍保留 `table_concurrency_conflict` 的原行状态校验和整体重试合同。此次并发结论只覆盖单实例、单库关系表 SQL 管理路径。直接调用底层 TableStore 的调用者沿用既有绕过 SQL 触发器的合同，不能据此宣称这些调用具有触发器约束、分布式可串行化或跨进程长事务保证。

提交锁使用最多 2,401 次尝试，每次 `Monitor.TryEnter` 等待不超过 50 ms，并有独立 120 秒墙钟上限；等待前、取得锁后及延迟执行期间检查调用方期限和取消。当前没有独立的行锁死锁图或死锁受害者协议：SQL 提交在一个 manager 锁下串行，禁止提交 body 调用任意应用回调；锁等待超时使用 `routine_commit_timeout`，锁总在 finally 释放。

宿主观测回调仍有既有边界：`MeterListener` 可能由持锁的引擎指标记录同步调用，监听器必须保持非阻塞且不得重入数据库写操作。静态复核发现重入 DDL 可与另一个 DDL 的 schema→manager 锁序冲突；旧提交与 TableStore 也存在这一路径，尚未执行专门复现，本切片不把全引擎指标回调的锁序风险计为已解决。上述死锁结论仅适用于受支持的纯 SQL 提交和遵守该约束的宿主。

存在延迟事件时，COMMIT 先把已有 ON DELETE CASCADE/SET NULL 生成的追加 mutation 缓冲到事务 overlay，使约束 body 能看到级联后的关系状态。延迟 body 后续更改删除集合时再展开级联，避免对未变化的集合反复扫描。自动生成的 FK 动作沿用现有合同，不派发合成 SQL 行触发器。每次展开最多生成 100,000 行级联 mutation，超限返回 `trigger_deferred_limit`；BFS、候选子行和 fallback 分桶循环检查取消及提交期限。

已展开的级联是本次提交内的实际动作：若延迟 body 随后重新插入被删除的父行，父行最终存在，但之前 CASCADE 删除的子行不会复活，SET NULL 的子外键也不会自动恢复。它与进入 COMMIT 之前 DELETE→INSERT 已归并为父行替换的情形不同；两种级联动作均有专门回归用例固定此边界。

| 预算 | 默认值 | 合同 |
|---|---:|---|
| `MaxDeferredTriggerInvocations` | 100,000 | 同事务保留事件上限；嵌入式和 Server 配置均最多 100,000 |
| `MaxDeferredTriggerBytes` | 64 MiB | OLD/NEW、定义文本和祖先链等存活成本的保守计费；Server 配置范围 1..128 MiB |
| `TransactionCommitTimeoutMilliseconds` | 30,000 ms | 从提交开始累计锁等待和协作执行时间；范围 1..120,000 ms |
| `MaxRoutineStatements` / `MaxRoutineDepth` / `MaxRoutineResultRows` | 64 / 8 / 10,000 | 保留原调用链预算，并同时受 COMMIT 请求预算约束；新 COMMIT 不能提高源调用已设的上限 |

多个源请求采用累积队列中的最严格事件数/字节上限，提交请求可以进一步收紧。执行恢复原祖先链，直接和间接递归仍拒绝；延迟不重置深度、源语句计数、结果行计数或 caller 审计。提交请求和原请求的取消都生效，执行期限取源请求与提交请求配置的最小值。

这些限制不等于整笔事务的峰值内存硬上限。FK 的既有 Scan/GetByIndex 路径仍可能在循环检查前物化候选行，SQL 的聚合/JOIN/排序使用各自内存治理；大扫描分配和原生 I/O 的暂停不能由队列字节预算完全约束。超时是协作式检查，不能把它解释成强制终止线程或硬性限制 fsync 时间。进入持久化决定后不再用提交期限强行中断同步日志操作。

## 提交阶段的 SQL 安全范围

约束 body 只接受关系表 INSERT/UPDATE/DELETE，可包含受支持的纯 SQL 子查询；WHEN 仍使用受限 OLD/NEW 行条件。定义时及提交执行时校验基础关系表、函数和表达式，提交中由 body 间接触发的普通触发器也经过同一检查。允许列表覆盖已审查的纯内置标量和聚合函数；禁止用户注册的标量/聚合/窗口/表值回调，即使它覆盖同名内置函数也会拒绝。

不允许 CALL、DDL、独立 SELECT、文件读取、JSON_FILE、GRAPH_TABLE、未准入的表值函数、视图、measurement、Document 或其他模型入口。代码校验具有节点数、深度和协作时间预算，不能通过提交 body 在 manager 锁内发起网络、外部脚本或任意应用代码。

## 错误、审计与恢复

| 情况 | 可观察合同 |
|---|---|
| 队列、级联生成量超限 | `trigger_deferred_limit`；源语句阶段撤销其保存点，COMMIT 阶段撤销整笔事务 |
| 原请求或提交取消 | `routine_cancelled`；持久化决定之前停止，清空事务队列和 mutation |
| 锁等待或延迟执行超时 | `routine_commit_timeout`；持久化尚未开始，可重新读取并重试整笔业务事务 |
| 递归、深度、语句或结果超限 | 复用 `trigger_recursion`、`routine_depth_limit`、`routine_statement_limit`、`routine_result_row_limit` |
| 依赖 schema 改变或不安全 SQL | `routine_dependency`，不执行任意应用回调 |
| 原行已被其他事务改变 | `table_concurrency_conflict`；当前事务结束，应重试整笔事务 |
| body 或最终表约束失败 | 保留既有例程/表约束异常边界；源行和动作都撤销，审计结算为失败或回滚 |
| 持久化确认/补偿结果未知 | 例程错误映射及审计为 `routine_commit_unknown` / `unknown`；直接嵌入式 COMMIT 可抛 `TableTransactionRecoveryException`，必须重开恢复并按幂等键核对 |

入队不记录 body 已执行成功。实际执行后的审计先等待最终提交，外层失败、回滚、提交未知均结算全部已执行动作；只有最终提交成功才报告 committed。既有 256 条内存审计窗口和快照导出不是 durable event log。

例程目录升级为独立 version 4，增加约束/延迟标志，读取 version 1/2/3 时使用立即触发器默认值。拒绝未知 flag bit 及不一致组合；支持的 v4 标志只有普通触发器 0 和延迟约束触发器 3。写入 v4 后旧引擎会拒绝打开，不应直接降级。此变更不修改主数据 FileHeader/BlockHeader、KV/WAL 或关系事务 journal 的格式。旧目录升级、备份恢复和进程终止恢复需要分别归档证据。

## AFTER COMMIT 的 durable outbox 边界

异步外部动作使用 `SqlOutboxWorker` 的显式 `ProcessBatchAsync`。生产者在原 SQL 事务或触发器中插入专用 outbox 表，只有事件行与源 DML 共享原子提交。worker 在独立领取事务落盘后、数据库锁之外调用处理器；外部投递和 ACK 不属于原 DML 提交边界。

每批按 `MaxBatchSize` 和 `BatchTimeout` 限定候选领取量与协作期限，默认 32 条和 30 秒，上限 1,000 条和两分钟；批量上限不限制筛选历史 done/dead 行所需的物理扫描量。没有隐式永久轮询线程，调度由宿主显式负责。持久化状态为 pending、leased、done、dead；领取记录 attempts、lease_token、lease_until，确认必须同时匹配有效租约。租约过期可重新领取；旧处理器不能确认新租约。

领取、ACK、重试和 dead 状态在返回前显式同步 outbox WAL，即使宿主关闭逐次写入同步也不能省略。同步失败禁用该表并报告提交结果未知，需关闭重开恢复。工作器拒绝从活动 SQL 事务或无事务 SQL 回调中重入；领取和确认使用带原行状态的内部 mutation，不执行专用表的用户 UPDATE 触发器，schema 校验会拒绝这种触发器。

失败按有上限的指数退避安排重试，达到领取次数或正文限制进入 dead；默认最多领取 5 次。处理器成功后、ACK 之前崩溃仍可能重复投递相同 EventId，因此是 at-least-once，消费者必须按 EventId 幂等。事件 ID 不因重试或数据库重开改变；done/dead 行保留，清理与人工重投由宿主负责。取消保留已领取但未确认的租约，后续过期恢复；处理器必须遵守取消令牌，SDK 不强制终止任意第三方代码，异步等待返回取消不证明不协作的处理器已经停止。

本次分别验证 worker 的领取/ACK 持久化、回退、取消、并发、过期重投、重开恢复和死信，并用独立子进程在本地可观察投递完成、ACK 前强杀；重开后相同 EventId 再次投递并持久确认。这里的投递目标是测试文件，不是生产外部消息系统。此切片不宣称 distributed exactly-once、持久 CDC 或生产级消息服务 SLO。

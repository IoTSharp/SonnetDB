# Issue #367：Int64 质量列游程压缩与 v7 段合同

日期：2026-11-05。代码基线为 `a7125ffb15c3d2182ff811036173316c75329ba9`；候选是该基线上的本地工作树修改，尚未提交、推送或合并。构建中的程序集信息仍显示基线 SHA，不能据此冒称候选已有提交。原始执行回执、TRX、真实 v6/v7 段与保留的旧 reader 在工作树的 `artifacts/issue367/`，不作为发行产物提交。

## 结论与已实现范围

原帖指出的 Int64 缺口成立：既有 `ValuePayloadCodecV2` 在启用 `DeltaValue` 时仍逐点写8字节整数。先加入4096点恒定质量的真实文件回归，修改前实际为 `raw=56642, compressed=56642`，断言失败；修复后该回归通过。

本次只实现一个确定的增量：显式 `ValueEncoding=DeltaValue` 下，对 Int64 块测量独立游程编码的完整载荷。只有严格小于原始8字节载荷时才使用，单点、交替/递增及无连续重复的整数仍回退旧raw载荷。编码不做差分，不窄化类型，支持 `long.MinValue/MaxValue`。默认时间戳和值选项仍为 `None`。

五组固定合成语料中，包含数值、质量、两份时间戳和全部段内开销的完整文件，常数/长游程场景缩小约36.4%～36.6%；交替/递增场景完整文件长度不变。此结果完成 #367 的一个实际压缩改进，不表示 M46-S02 全部编码、共享时间戳、浮点新算法、WAL压缩或生产每点2～3字节目标已经实现。

## 编码、版本与回退合同

- 每个新写段的 `SegmentHeader.FormatVersion`、`SegmentFooter.FormatVersion` 升为 **v7**，包括没有选中RLE的段。旧引擎会拒绝v7段；这不是只对压缩块生效的兼容变更。
- 新值编码为独立 `BlockEncoding.Int64Rle=16`。每个run写 `Int64 little-endian value` 加正的 `UInt32 varint length`；run长度不超过剩余声明点数，varint最多5字节、必须是最短编码。旧 `DeltaValue` 的 Int64 含义继续是逐点8字节raw，旧块不能重新解释。
- `SegmentHeader` 64B、`BlockHeader` 80B、`SegmentFooter` 64B的布局不变。通用 `FileHeader/WAL/Catalog` 的版本和布局没有改变；真正发生变更的是已有独立版本字段的 `.SDBSEG` 格式。
- 新reader兼容v2～v6，v7沿用v6的内嵌sketch/HNSW、mini-footer和CRC布局。footer自校验门槛固定为v6起，避免当前版本升到v7后遗漏旧v6校验。
- Open拒绝未知编码标志、v6中的新flag、非Int64使用RLE、空RLE块及互斥值编码组合；解码拒绝截断原值/varint、零长度、过长/溢出/非最短varint、run总数不匹配和尾部字节。范围读仅填充目标点，但仍检查全部run和尾部，避免请求区间之外的损坏被隐藏。
- 升级前关闭数据库并完整备份，再用新引擎读取原有段；后续flush/compaction按新版本生成段。降级必须恢复升级前备份，升级后的新写入另行导出或回补，不能靠换回旧二进制或删除段文件完成无损回滚。此切片没有原地降版工具。

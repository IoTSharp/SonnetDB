# SonnetDB 总里程碑：十四套能力

**核查日期：2026-09-13**

**当前代码基线：ff55b25（主分支）**

本文把此前关于 IoTDB、TDengine、TimechoAI、多模型数据库、AI/RAG、生产验证和数据库榜单的结论重新核对，并收敛为一个总里程碑。它是路线图的产品级收口，不替代 M19、M20、M25、M27、M35、M36、M40、M41、M42 的具体实现任务。

**状态图例：** ✅ 所述交付已完成；🟡 实现/本地验证完成，真机或发布证据待补；🚧 部分完成；❌ 已执行但未通过；📋 已规划、尚未实现；⏳ 验证或外部结果待执行；➡️ 已移交；⏸️ 暂停。

**编号规则：** 既有 PR 工作项沿用原编号，新增项接续 #381，从 #382 至 #402 按升序排列。这些是 ROADMAP 的 PR 工作项编号，不表示 GitHub 已创建或合并同号 PR；✅ 只覆盖该行说明的交付。本轮完成 #382 的本地文档整理，其余新增项仍待实施。PR 表按编号查找，实际执行按步骤与依赖推进，每个 PR 只交付一个工作项。

## 一、重新核对后的结论

### 1. SonnetDB 的定位判断仍然成立

SonnetDB 最有价值的方向不是在每一个单项指标上击败专用数据库，而是把边缘部署、工业数据、多模型访问、语义检索和受治理 Agent 访问放进同一个可运行的引擎。这个方向能够解释时序、文档、对象、消息、图、向量和 Copilot 为什么需要共同存在，也能解释为什么要保留单机、AOT、零运行时第三方依赖和数据库目录持久化边界。

对 IoTDB、TDengine 和 TimechoAI 的学习重点应当是工业时序的工程闭环：高基数与多 measurement 容量、写入与查询基准、集群/边缘拓扑、订阅与流式处理、设备语义、告警和 AI 数据产品化。它们不能直接证明 SonnetDB 已经具备这些能力，SonnetDB 也不应为了追赶而改变自己的多模型边界。

对 ArangoDB、SurrealDB、MongoDB Atlas、Couchbase、Redis、Oracle、MarkLogic、Neo4j、Milvus、Weaviate、Qdrant、LanceDB、Elasticsearch/OpenSearch、Vespa 等产品的共同学习点，是模型之间的查询入口、索引生命周期、失败恢复、资源边界、兼容性声明和公开基准。多模型产品的核心竞争力不是菜单上列出更多模型，而是用户能否完成一条从写入、查询、分页、更新、失败、重启到备份恢复的完整旅程。

### 2. “九种模型”与“十四套能力”不是两套互相竞争的口径

当前仓库确实已经形成九个原生数据模型的实现入口：时序、关系、键值、文档、全文、向量、对象、消息队列和属性图。九者的成熟度不同，Graph 仍是 Graph Beta 范围；九模型都有代码和产品入口，不等于九模型都已经完成容量、恢复、跨端 parity 和生产发布证据。

最终产品口径采用 **九种原生数据模型 + 五种平台能力 = 十四套数据库能力**：

1. 九种模型保留现有产品主线。
2. 空间/地理/轨迹作为第十项跨模型数据库能力纳入总能力清单；它已经在 M15~M17 交付基础，不重新包装成新的模型。
3. 流处理/订阅、CDC/边缘同步/复制、AI/RAG、治理与运维作为四项平台能力补齐十四行。

因此，“十四”是产品能力总数，“九”是当前公开的原生数据模型数。榜单入榜属于十四项能力共同的生态发布门禁，不计作第十五种数据模型。

### 3. 当前最大问题不是功能数量，而是闭环和证据

已有审计仍然有效，但需要按 2026-09-13 的主分支状态理解：

- ❌ M20 仍未通过当前 nightly 门禁：截至 2026-09-13，最近七次 scheduled（09-07 至 09-13）为 4 次成功、3 次失败，成功率约 57%，低于要求的 95%。此前 08-30 至 09-05 的全失败窗口保留为历史证据；本地已经验证启动修复，但连续七次远程成功和稳定的双 profile 对账仍未形成。
- 🟡 M19、M25、M29、M40 主要剩固定硬件、干净安装、外部对拍、Native AOT 或长稳等现场证据；本机 smoke 不替代这些证据。
- 🚧 M27 的 Copilot/MCP/Provider 已有真实代码路径，但真实目标模型的质量、延迟、成本、双网部署和跨进程续流仍未闭环；M14 实际是 Microsoft.Extensions.AI 加自研 CopilotAgent，不能写成 Microsoft Agent Framework。
- 🚧 M35 已经有语义内容、图片检索和 RAG Core 地基，持久化 writer、resume、派生索引实际应用、融合质量和媒体扩展仍未完成。
- 🚧 M36 已经关闭部分 KV 原子操作和对象有界分页问题，但九模型 golden journey、对象传输恢复、MQ 消费恢复、全文工作流和 SQL 端到端有界结果仍未整体关闭。
- 🚧 M41/M42 已完成大量本地规划器和资源边界切片，但固定 x64/ARM64、统一语料、168 小时混合负载和发布门禁仍是独立证据。

这些项目不能合并成一个“全部完成”的状态；总里程碑只在每项能力同时满足实现、入口、测试、文档和相应证据后关闭。

### C. 五项平台能力的缺口

M14、M15~M18、M26~M30、M34 已交付 Agent UX、空间/轨迹、工具链、连接器、协议接入、Modbus 和管理面等重要组成部分。仍缺少两条没有独立路线的能力：

- 📋 流处理/订阅需要从现有 SSE、MQ、MQTT 和 outbox 中抽取统一的连续查询与可恢复消费合同，归 #391~#395。
- 📋 CDC/边缘同步/复制需要独立定义变更格式、检查点、冲突、schema 演进、离线重放和拓扑，归 #385~#390。

✅ 两项的 PR 规划已在本文登记；📋 具体实现与验证尚未开始。

#### 步骤 1：🚧 能力清单与证据底座（#382~#384）

- 固定十四项名称、类型、supported / partial / planned / not_planned 状态和公开边界。
- 为每项能力登记真实入口、Core/Server/SDK/CLI/Web/Studio 覆盖、测试、恢复方式、性能指标和原始报告路径。
- 将 M20、M19、M25、M27、M29、M35、M36、M40、M41、M42 的遗留项映射到十四项能力，禁止重复创建已完成实现。

**退出条件：** 任一能力都能回答“代码在哪里、用户从哪里调用、失败时如何返回、重启后如何恢复、当前不能做什么、哪份证据支持声明”。

4. 完成 M19/M25/M42 的固定硬件和跨架构验证准备，确保每份报告包含 commit、硬件、配置、原始样本、P50/P95/P99、内存/GC/I/O 和正确性对账。

**退出条件：** M20 门禁通过；其余事项按原 P1/P2/P3 优先级逐项完成。每项都注明实现、验证和失败范围，原 gap 的优先级不因本次编号整理统一升为 P0。

## JSON 更新合同

支持固定标量、对象/数组子树、整根容器、固定OwnsMany元素对象，以及固定primitive集合元素目标和JSON集合原生标量右值。Guid、日期/时间/offset/ticks、decimal、二进制和enum/converter的常量/闭包值使用模型JSON编码器。每个ExecuteUpdate是一条服务器UPDATE，路径和值参数化，SQL NULL遵循EF优化后的NULL常量形状；同列setter按声明顺序，右值读取更新前行。

目标外未知JSON和数字原文保留，替换子树内部以新模型值为准。缺失父级、错误父级或数组越界使整条语句拒绝，不补建父级或追加元素。应用须显式把Token/自行维护的RowVersion写入Where并检查影响行数，数据库不自动替应用递增版本。

动态/负数索引、条件元素目标、任意集合LINQ投影以及非原生/converter逐行右值仍在SQL发送前拒绝。EF Provider保留其运行时模型的非NativeAOT边界；Core/Server/CLI的AOT与JSON source-generation/手写读写合同独立验证，没有反射JSON或警告压制回退。

## 迁移前检查

1. 停止迁移及业务写入，备份当前数据库目录和对应Server配置/实例资源；记录正在运行的Provider/Core/Server版本和来源。
2. 核对实际表、列、索引、FK/CHECK、业务数据及`__EFMigrationsHistory`，确认迁移前状态一致。历史行存在与否不足以证明业务DDL/DML是否提交。
3. 在隔离副本以匹配候选完成Up/Down、失败回滚、同连接重试和独立进程重开；核对本次适用的真实进程强杀证据，不能把它写成物理掉电验收。
4. 使用同一候选包和匹配Server完成两个应用验收，保留精确SQL、影响行数、包/DLL/source/服务身份，再执行批准的升级。

## 旧5.0.0已产生部分迁移时

#392官方5.0.0负控已实证：迁移历史中缺少Shipping，而Stock已由7变为5。升级Provider不会自动撤销这些旧的独立提交。

此时必须保留失败现场、停写并备份现状，再核schema/索引/FK/业务数据/历史。可恢复升级前的一致备份并回补业务数据，或针对该迁移执行经审查的修复方案。**不能只补历史行，也不能把盲目再次Migrate当作修复。** 具体恢复/回补方案取决于已发生的写入，须通过业务核对证明一致。

## 回退边界

保留升级前一致备份、原版本程序和配置。新候选所含main会写v7 `.SDBSEG`，新reader兼容v2～v6，旧reader拒绝v7；因此不能在已写新段的目录上直接换回旧程序。回退应恢复与旧程序匹配的升级前备份，再按已核对的方案回补数据。WAL/Catalog/协议及本次JSON/DDL修复没有另行改布局，不能因此推断所有模型都可原地降级。

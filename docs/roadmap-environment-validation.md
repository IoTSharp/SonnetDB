# SonnetDB 环境、固定硬件、掉电与长稳验收路线

核查日期：2026-11-11（Asia/Shanghai）。本路线从能力实现路线中独立出来，专门管理线上 Demo 服务器、固定目标硬件、现场生产环境、物理掉电/介质故障和长期稳定运行的资格验收。

全仓代码与能力推进顺序仍以[根路线图](../ROADMAP.md#当前推进顺序)为准。本文件不重新实现 KV、时序、SQL、Graph、日志、连接器或管理面能力，也不把现场运行证据倒灌成代码完成证据。它只回答一个问题：**某个已经声明支持的候选版本，在指定 Demo 或现场生产环境中是否取得了可追溯的运行资格。**

## 范围和状态

本路线包含以下环境层：

- 线上 Demo 服务器的版本绑定、真实负载、容量、恢复和连续运行；
- 现场生产目标的硬件、OS、CPU/内存/磁盘/文件系统、电源链路和部署身份；
- 固定 x64/ARM64 目标机上的容量、尾延迟、资源、I/O 和恢复；
- 物理掉电、介质刷新失败、半写文件、设备重启和恢复后的数据对账；
- 168 小时/7 天长稳、混合读写、后台维护、异常重启、积压和资源趋势；
- 用户后续提供的 Demo/现场日志、原始报告和故障时间线分析。

环境资格不改变代码路线的退出条件。单元测试、差分测试、确定性进程强杀、损坏/满盘注入、旧格式拒绝、协议解析、取消和本地恢复仍在各自能力路线中完成。环境路线也不能被一次进程强杀、一次 hosted job、一次 quick profile 或一份没有电源/介质证据的日志替代。

状态使用以下含义：

| 状态 | 含义 |
| --- | --- |
| `PLANNED` | 已登记环境任务，目标、版本或阈值尚未冻结。 |
| `READY` | 目标、候选、语料、命令、停止条件和证据位置已冻结，可以运行。 |
| `PASS` | 指定环境层按冻结合同完成，原始证据和独立读回齐全。 |
| `FAIL` | 已运行但不满足阈值或数据对账。保留原始失败，不降低门槛。 |
| `NOT_RUN` | 本轮没有运行，或用户尚未提供现场/Demo证据。 |
| `UNKNOWN` | 运行或日志不完整，无法证明结果。 |
| `DEFERRED` | 能力或代码切片已完成，环境资格后置，不阻断普通代码交付。 |
| `BLOCKED` | 缺少明确的目标、维护窗口、候选或授权，无法安全开始。 |

`PASS` 只适用于它所在的目标、版本、语料、配置和时间窗。Demo PASS 不升级为现场生产 PASS；x64 PASS 不升级为 ARM64 PASS；进程强杀 PASS 不升级为物理掉电 PASS；168 小时 PASS 不升级为永久稳定或高可用。

### ENV-RELIABILITY：掉电、恢复与实例边界

本路线的物理掉电测试必须由目标环境的电源/存储条件产生并留痕，不能由 `Process.Kill`、追加 torn WAL 或模拟异常代替。每一轮至少登记：

1. 掉电前最后一个已确认写入、WAL/checkpoint/segment/manifest 位置；
2. 电源事件时间、持续时间、设备/UPS/控制器状态和是否存在写缓存；
3. 重启前后的文件系统、磁盘错误、介质 SMART/控制器日志（如果目标提供）；
4. 数据库、共享 LSM、时序、文档、对象、全文/向量派生索引、MQ offset、CDC/任务 checkpoint 和外部对象的逐项对账；
5. 恢复耗时、失败/未知结果、重试次数、恢复后继续写入和再次重开；
6. 原始日志、命令/设备回执、版本/配置哈希和采集缺口。

单库 `sndb backup`、Server `.system/mq` 快照、身份/配置和外部对象属于不同恢复域。恢复一项不代表整个 Server 实例恢复；日志缺少电源状态、介质刷新和完整性链路时，不能证明“物理掉电零丢失”，但也不能因此否定已有代码实现。

## 分拆后的代码路线出口

### M48

- `L20A`：支持矩阵、候选清单、AOT/安装脚本、权限/预算/恢复的本地可复现证据和操作手册；可以在没有现场长稳时交付代码切片。
- `L20B`：固定硬件、现场采集器/生产负载、168小时、安装首跑和发布资格，转入 `ENV-01/ENV-02/ENV-04/ENV-06`；Logstash 软件协议对接仍由 L06/G1 代码候选验证。
- G4 只有在 L20A 和适用代码门禁完成时形成候选；环境资格缺失时标记 `ENV NOT_RUN/DEFERRED`，不把 R1 现场资格写成能力实现失败。

- `T30A`：代码、协议、精度、格式、旧端拒绝、AOT/包消费者、迁移/恢复和可复现门禁；留在主路线。
- `T30B`：固定 x64/ARM64 成本、168小时多库混合精度、现场生产消费者；T32 仅在本批明确纳入真实授时时追加；全部进入本路线。

## 日志接收与分析合同

用户后续提供线上 Demo 或现场生产日志后，按以下顺序分析：

1. 先核对文件来源、采集时间、时区、完整性摘要、候选 SHA/包 digest 和目标身份；缺失项保持 `UNKNOWN`。
2. 重建运行时间线：启动、确认写、WAL/checkpoint、flush/compaction、查询、积压、异常、重启、电源事件和恢复。
3. 分离逻辑计数与物理证据：应用 ACK、OS flush、fsync 调用、设备/电源/介质日志不是同一事实。
4. 分别统计吞吐、P50/P95/P99、RSS/GC、I/O、锁/队列、重试、缺失/重复/值差异、恢复时间和未观测区间。
5. 将结果绑定到 ENV-00～ENV-06 的具体目标和版本，更新 `PASS/FAIL/UNKNOWN/NOT_RUN`，不修改原始日志、不用摘要覆盖失败样本。

日志能够证明日志实际记录的版本、时间窗、负载、故障和恢复结果；缺少电源、介质或完整性链路时不能证明物理掉电零丢失。环境分析也不替代代码测试、API 合同和修复任务。
